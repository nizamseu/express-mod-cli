# Admin Panel Plan (`express-mod-cli add-admin`)

A built-in, Django-admin-style panel for projects generated by express-mod-cli.
It is written from scratch: **no AdminJS**, no React, no build step.

Status: plan, nothing implemented yet. Target release: the version after `add-auth` ships.

---

## 1. Goal

One command gives a generated project a working admin panel:

```bash
express-mod-cli add-auth          # already exists (users, roles, JWT)
express-mod-cli add-admin         # new
npm run auth:set-role -- me@example.com admin
npm run dev                       # open http://localhost:5000/admin
```

What the admin sees, modelled on Django admin:

| Django admin               | Our admin                                                        |
| -------------------------- | ---------------------------------------------------------------- |
| Login page                 | Login with the existing `/auth/login` (role must be `admin`)      |
| Site administration        | Dashboard: every module, grouped, with **Add** / **Change** links |
| Change list                | Table with search, sort, filters, pagination, bulk delete         |
| Add / change form          | Form built from the module's fields, with inline validation errors |
| Delete confirmation        | Confirmation page (no browser `confirm()`)                        |
| Recent actions / My actions | Audit log of every add / change / delete                         |
| Users / Groups             | Users list: change role (passwords never shown)                   |
| Light / dark toggle        | Light, dark and system themes, plus custom themes                 |

### Non-goals (first release)

- Relations / foreign-key pickers (modules have no relations yet).
- File uploads, rich-text editing, CSV import/export.
- Per-model permissions (only "is admin" for now).
- A dashboard with charts.

These are listed in [Phase 10](#phase-10--later).

## 2. Key design decisions

### 2.1 Reuse each module's controller and validation

Every module already has `getAll`, `getById`, `create`, `update`, `remove` in its controller and
`create…Schema` / `update…Schema` in its validation file. The admin API mounts **the same
handlers** behind an admin guard:

```
/products              -> public (or --auth / --role) routes  -> products.controller
/admin/api/r/products  -> requireRole('admin') + audit log    -> products.controller (same functions)
```

So the admin automatically gets the module's pagination, sorting, search, Zod validation,
`404`s and `409` unique errors, and there is a single place to change business logic.

### 2.2 The UI is static HTML + plain JavaScript

- Served by `express.static`, with no template engine, bundler or framework.
- Hash routing (`#/products`, `#/products/42`), so the server only ever serves `index.html`.
- Talks to `/admin/api/*` with `fetch`, like any other client.
- No inline `<script>` or `<style>`, so the project's existing `helmet()` CSP works unchanged.
- The same files work for JavaScript and TypeScript projects.

> This replaces the earlier idea of server-rendered EJS pages: because of 2.1, a static UI
> needs no new dependencies and no second copy of the CRUD logic.

### 2.3 Login reuses `add-auth`

`add-admin` requires `add-auth`. The UI logs in with `POST /auth/login`, keeps the **access token in
memory only** (never `localStorage`), and gets a new one from `POST /auth/refresh` (refresh token
cookie, `httpOnly`, path `/auth`) on page load and on a `401`. Access is decided on the server by
`requireRole(<admin role>)`. The UI hiding things is only for convenience.

Because the API uses a `Bearer` header and not a session cookie, it is not open to CSRF, so no
CSRF tokens or session store are needed.

### 2.4 Field metadata lives in a per-module `*.admin` file

The CLI knows every field when it runs `add products name:string price:number …`, but it doesn't
save that information today. From now on `add` also writes `src/modules/products/products.admin.{js,ts}`
containing the fields and the display options. It is plain code that users can edit, just like
the model.

Modules created before this (or created without the admin file) use **runtime introspection**
of the Mongoose schema / Sequelize attributes instead.

### 2.5 The UI files live outside `src/`

TypeScript projects compile `src/` to `dist/`, and `tsc` doesn't copy `.html`/`.css`. The UI therefore
lives in `admin-ui/` at the project root and is located with
`path.join(__dirname, '..', '..', 'admin-ui')`, which works from both `src/admin/` and `dist/admin/`.

## 4. Contracts

### 4.1 `products.admin.js` (generated by `add`, editable)

```js
const controller = require('./products.controller');
const { createProductSchema, updateProductSchema } = require('./products.validation');

module.exports = {
  name: 'products',              // URL segment, = module folder
  label: 'Products',
  singularLabel: 'Product',
  group: 'default',              // Dashboard section (defaults to the connection name)
  idField: '_id',                // 'id' for SQL

  // Copied from the "add" command line. Edit this when you change the model.
  // Set to 'auto' to read the fields from the model at startup instead.
  fields: [
    { name: 'name', type: 'string', required: true, unique: true },
    { name: 'price', type: 'number', required: true },
    { name: 'stock', type: 'integer', default: 0 },
    { name: 'status', type: 'enum', values: ['draft', 'published'], default: 'draft' },
    { name: 'releasedAt', type: 'date', optional: true },
  ],

  list: {
    columns: ['name', 'price', 'status', 'createdAt'],  // Default: first 4 fields + createdAt
    searchable: ['name'],          // Must match the controller's SEARCHABLE_FIELDS
    sortable: ['name', 'price', 'stock', 'status', 'releasedAt', 'createdAt', 'updatedAt'],
    filters: ['status'],           // enum and boolean fields (needs the filter support in Phase 3)
    defaultSort: '-createdAt',
  },

  form: {
    hidden: [],                    // Not shown in the form
    readonly: [],                  // Shown, not editable
    help: { price: 'In BDT' },     // Text under an input
  },

  // Title of one record in lists, page titles and the audit log
  display: (item) => item.name,

  controller,
  schemas: { create: createProductSchema, update: updateProductSchema },
  actions: { add: true, change: true, delete: true },  // Turn actions off per module
};
```

### 4.2 Field type → UI

| Field type | Input                         | Sent as                       | Cell display            |
| ---------- | ----------------------------- | ----------------------------- | ----------------------- |
| `string`   | `<input type="text">`         | string                        | text                    |
| `text`     | `<textarea>`                  | string                        | first 80 chars          |
| `number`   | `<input type="number" step="any">` | number                   | locale number           |
| `integer`  | `<input type="number" step="1">`   | number                   | locale number           |
| `boolean`  | checkbox (or a 3-state select if optional) | `true` / `false` / `null` | ✓ / ✗ / –   |
| `date`     | `<input type="date">`         | `YYYY-MM-DD`                  | locale date             |
| `enum`     | `<select>` with the values    | string                        | badge                   |
| `id`, `createdAt`, `updatedAt` | read-only text | never sent              | locale date / id        |

Form value rules:

- Empty optional input → `null`. Empty required input → the client lets Zod report it.
- Fields with a default show the default when adding.
- **Edit sends only the fields that changed** (PATCH), so the request doesn't touch values that
  haven't changed.
- A `400` from `validate()` returns `errors: [{ field, message }]`. Each message is shown under its
  input, and messages without a field go in a banner at the top.
- A `409` is shown as "A Product with this value already exists" (on the unique field if there is
  only one).

### 4.3 Admin API

All routes are under `<admin path>/api` and need `requireRole(<admin role>)`.

| Method | Path                     | Purpose                                                                |
| ------ | ------------------------ | ---------------------------------------------------------------------- |
| GET    | `/schema`                | Site title, current user, resources with fields/list/form (no functions) |
| GET    | `/r/:name`               | → `controller.getAll` (same query: page, limit, sort, search, filter)   |
| GET    | `/r/:name/:id`           | → `controller.getById`                                                 |
| POST   | `/r/:name`               | `validate(create)` → `controller.create` → audit "add"                  |
| PATCH  | `/r/:name/:id`           | `validate(update)` → `controller.update` → audit "change" (changed fields) |
| DELETE | `/r/:name/:id`           | `controller.remove` → audit "delete"                                   |
| GET    | `/logs?mine=1&limit=10`  | Recent actions (dashboard sidebar)                                     |
| GET    | `/logs?resource=products&objectId=42` | History of one record (Phase 10)                          |
| GET    | `/users`, PATCH `/users/:id/role` | User management (Phase 7)                                     |

When an action is turned off in `actions`, its route is not mounted, so the API returns `404`.

### 4.4 AdminLog record

| Field         | Notes                                              |
| ------------- | -------------------------------------------------- |
| `userId`      | From `req.user.id`                                  |
| `userEmail`   | Copied, so the log still reads well if the user is deleted |
| `action`      | `add` / `change` / `delete`                         |
| `resource`    | Module name                                         |
| `objectId`    | String                                              |
| `objectLabel` | `display(item)` at the time, max 200 chars          |
| `changes`     | List of changed field names (never the values)      |
| `createdAt`   |                                                     |

It is stored on the auth connection (`project.auth.connection`), next to the users.

## 5. Phases

Sizes: **S** ≈ under half a day, **M** ≈ 1–2 days, **L** ≈ 3+ days.

### Phase 0: Prerequisites (S)

- [ ] Finish and commit `add-auth` (it is uncommitted work right now). The admin builds on
      `requireRole`, `/auth/login`, `/auth/refresh`, `/auth/me` and `auth:set-role`.
- [ ] Make sure `/auth/me` returns `role` (the UI uses it to show "no access" instead of an empty panel).
- [ ] Decide the open questions in [section 8](#8-open-questions).

### Phase 1: Field metadata for every module (M)

CLI changes:

- [ ] `lib/templates/adminTemplates.js`: `generateModuleAdminContent({ name, language, dbType, fields })`
      → `products.admin.{js,ts}` (section 4.1). It reuses `searchableFields` / `sortableFields` from
      `fieldTemplates.js` so the admin and the controller always agree.
- [ ] `addModule.js`: when `project.admin` is set, write the admin file and insert the resource into
      `src/admin/registry` below `// ADMIN_IMPORTS` and `// ADMIN_RESOURCES`. Check those markers up
      front with `assertMarkers`, like the route markers.
- [ ] `--no-admin` flag on `add` (for modules that must not show up in the admin).
- [ ] Remember in `.expressmodrc.json` which modules opted out: `"admin": { "path": "/admin", "exclude": [] }`.
- [ ] `projectConfig.js`: `loadProject` / `saveProject` handle `admin`.

Generated project:

- [ ] `src/admin/introspect`: builds the `fields` list from a model when `fields: 'auto'`.
  - Mongoose: `schema.paths` → `instance` (String/Number/Boolean/Date), `isRequired`,
    `enumValues`, `options.unique`, `defaultValue`; skip `_id`, `__v`, timestamps.
  - Sequelize: `Model.getAttributes()` → `type.key` (STRING/TEXT/DOUBLE/INTEGER/BOOLEAN/DATE),
    `allowNull`, `validate.isIn`, `unique`, `defaultValue`; skip `id`, timestamps.
  - Unknown types become a read-only text field, so nothing breaks.

Done when: `add products name:string …` in an admin project creates `products.admin.js` and registers
it, and a module whose admin file says `fields: 'auto'` gives the same field list.

### Phase 2: Admin backend (M)

- [ ] `admin.config`:
  ```js
  module.exports = {
    title: process.env.ADMIN_TITLE || 'Administration',
    path: '/admin',              // Also written to .expressmodrc.json
    role: 'admin',
    pageSize: 20,
    themes: ['light', 'dark'],   // Files in admin-ui/css/themes
    defaultTheme: 'system',      // 'light' | 'dark' | 'system'
    groups: {},                  // e.g. { default: 'Shop', analytics: 'Reports' }
  };
  ```
- [ ] `registry`: holds the resources, rejects duplicate names at startup, resolves `fields: 'auto'`.
- [ ] `admin.routes`:
  - `GET <path>` and `<path>/` → `index.html`; `express.static(admin-ui)` for assets.
  - `<path>/api` router: `requireRole(config.role)` → `/schema`, `/logs`, then one sub-router per
    resource (`/r/<name>`) built from its controller + schemas + `auditLog`.
  - `Cache-Control: no-store` on API responses.
- [ ] The CLI adds the `app.use('<path>', adminRoutes)` line to `src/app` below `// ROUTE_MIDDLEWARE`.
      It goes before the 404 handler, which is already true for that marker.
- [ ] `/schema` serializes resources without `controller`, `schemas` or `display` (no functions or
      internals leak).

Done when: with an admin token, `curl /admin/api/schema` lists the modules and
`curl /admin/api/r/products` returns the same JSON as `/products`. A `user` token gets `403` and no
token gets `401`.

### Phase 3: Filters in module list endpoints (S–M)

Change lists need filters (Django's right-hand sidebar). Today `getAll` only supports `search`.

- [ ] Controller template: `FILTERABLE_FIELDS` = enum + boolean fields. `getAll` reads
      `?status=draft&inStock=true`, validates each value against the field, and adds it to the
      Mongo filter / Sequelize `where` (combined with `search` using AND).
- [ ] Invalid value → `400` (same style as `parseListQuery`).
- [ ] `listQuery` helper: `parseFilters(query, filterable)`.
- [ ] This also improves the public API, so document it in the README "Pagination, Sorting and Search" section.
- [ ] Modules created before this have no filter support: their admin file gets `filters: []`
      and the UI hides the sidebar.
- [ ] Later: date range filters (`?releasedAt[gte]=…`).

### Phase 4: Admin UI MVP (L)

Shell:

- [ ] `index.html`: header (site title, user email, theme toggle, log out), `<main id="app">`, and
      `<script type="module" src="js/main.js">`.
- [ ] `main.js`: on load, call `/auth/refresh`. If that works → `/auth/me` → if the role is wrong,
      show the "no access" page; otherwise load `/schema` and start the router. If it fails → login.
- [ ] `api.js`: adds `Authorization`; on a `401` it refreshes once and retries; if the refresh also
      fails it goes to login. It parses `{ success, data, pagination, message, errors }`.
- [ ] `dom.js`: `h(tag, attrs, ...children)` that only uses `textContent`, which prevents XSS from
      record data.

Pages:

- [ ] **Login**: email, password, error message, "you are not an admin" message, and the rate-limit
      message (`429` from auth).
- [ ] **Dashboard**: one table per group (Django's app sections) with each module's label and
      **+ Add** / **Change**. The "Recent actions → My actions" sidebar comes from `/logs?mine=1`
      (Phase 6; hidden until then).
- [ ] **Change list** (`#/products`):
  - Title, "Add Product" button, total count ("23 products").
  - Search box, shown only when `searchable` is not empty; uses `?search=`.
  - Column headers sort by clicking (asc → desc → default), using `?sort=`; shows an arrow.
  - Filter sidebar (enum/boolean): "All" plus each value; uses `?status=`.
  - Rows: the first column links to the edit form.
  - Checkbox column + "Delete selected" → delete confirmation page listing them.
  - Pagination: first / prev / page numbers / next / last, and a page-size select (max 100).
  - The URL keeps the state (`#/products?page=2&sort=-price&status=draft`), so back/refresh/sharing work.
  - Empty state ("No products yet. Add one").
- [ ] **Add / change form** (`#/products/add`, `#/products/:id`):
  - Inputs from section 4.2, required marker `*`, help text, defaults when adding.
  - `id`, `createdAt` and `updatedAt` shown read-only when editing.
  - Buttons: **Save**, **Save and add another**, **Save and continue editing**, **Delete** (edit only).
  - Inline errors (`400`), unique error (`409`), "not found" (`404`), and a warning when leaving
    with unsaved changes.
  - Success message banner after saving ("The product "Phone" was changed successfully.").
- [ ] **Delete confirmation** (`#/products/:id/delete`, and the bulk version): "Are you sure?", the
      list of objects, and Yes / No. Bulk delete runs the DELETEs one by one and reports any failures.
- [ ] **Not found / no access** pages.

Quality:

- [ ] Responsive: the sidebar collapses on narrow screens, the table scrolls horizontally inside its
      own box, and forms are a single column.
- [ ] Accessibility: real `<label>`s, `<table>` with `<th scope>`, focus moves to the page heading on
      navigation, errors linked with `aria-describedby`, everything usable by keyboard.
- [ ] No external CDN: everything is served from the project, so it works offline and with the default CSP.

### Phase 6: Recent actions / audit log (M)

- [ ] `adminLog.model` (Mongoose + Sequelize) and `adminLog.repository` (`create`, `listRecent`).
- [ ] `auditLog(resource, action)` middleware: wraps `res.json` to capture the response body, then
      on `finish` with status 2xx writes the log entry. For `change`, the changed fields are
      `Object.keys(req.body)` after validation. Logging errors are reported with `console.error` and
      **never** fail the request.
- [ ] `GET /api/logs`: newest first, `mine`, `resource`, `objectId` and `limit` (max 50).
- [ ] Dashboard sidebar: icon per action (+ / ✎ / ✕), object label linking to the record (plain text
      if deleted), and the resource label underneath, like Django.

### Phase 7: Users in the admin (S–M)

- [ ] A built-in "Users" resource (always registered when the admin exists), built on the auth
      repository and **not** on a module controller:
  - list (email, name, role, createdAt), search by email/name, filter by role;
  - change role (select from the roles in the User model);
  - never shows or accepts `passwordHash`;
  - you cannot remove your own admin role (so you can't lock yourself out).
- [ ] Logged in the audit log like any other change.
- [ ] Later: "set a new password" and "log out everywhere" (revoke refresh tokens).

### Phase 8: Themes and branding (S)

- [ ] `base.css` uses only CSS variables: `--bg`, `--surface`, `--text`, `--muted`, `--border`,
      `--primary`, `--primary-text`, `--header-bg`, `--header-text`, `--danger`, `--success`,
      `--radius`, `--font`.
- [ ] `themes/light.css` and `themes/dark.css` set those variables under `[data-theme="light"]` / `[data-theme="dark"]`.
- [ ] `theme.js`: cycles through system → light → dark (and any extra themes from `config.themes`).
      The choice is stored in `localStorage` (inside try/catch), and "system" follows `prefers-color-scheme`.
- [ ] **Adding a custom theme**: copy `light.css` to `themes/ocean.css`, change the variables, and
      add `'ocean'` to `themes` in `admin.config`. It then appears in the toggle.
- [ ] Branding: `title` (header and `<title>`), an optional `logo` (a file in `admin-ui/`), and the brand
      colour with `--primary`.

## 6. Security checklist

- [ ] Every `/admin/api` route is behind `requireRole(config.role)`, checked on the server.
- [ ] The access token is kept in memory only; the refresh token stays in the existing `httpOnly` cookie.
- [ ] Data goes into the page through `textContent` only (no `innerHTML`), so record data can't run as script.
- [ ] Default `helmet()` CSP stays on: no inline scripts or styles, no CDN.
- [ ] Login keeps the auth rate limit (`AUTH_RATE_LIMIT`).
- [ ] `/schema` and `/users` never expose `passwordHash`, tokens or internals.
- [ ] Writes go through the module's Zod schema, so unknown fields are dropped.
- [ ] The audit log stores field **names**, not values (no secrets in logs).
- [ ] An admin can't remove their own admin role.
- [ ] `Cache-Control: no-store` on API responses.

## 8. Open questions

1. **Default path**: `/admin` (familiar) or something less guessable? Proposal: `/admin`, changeable
   with `--path`.
2. **Without auth**: should `add-admin` fail with "run add-auth first", or run `add-auth` itself?
   Proposal: fail when not interactive, offer to run it when interactive.
3. **Filters (Phase 3)** change the public list API of new modules. Is that OK, or should filters be
   admin-only? Proposal: public, because it is useful and documented.
4. **Role**: a single `admin` role, or also `staff` (can view and edit, but not delete or manage users)? Proposal: `admin`
   only now; `staff` with per-module permissions later.
5. **UI language**: English first with all strings in `i18n.js`, Bangla as the first extra language?
